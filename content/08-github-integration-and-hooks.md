# 探索 GitHub 集成与 hooks

这一节，你会学到怎么在**终端之外**、通过 **GitHub 集成**来用 Claude Code：怎么配置它来**评审拉取请求（pull request）、修复 issue**。然后你会学到怎么用 **Claude Code 的钩子（hooks）**，在使用工具的前后执行代码。开始吧。

## 收尾：删掉工作树并推到 GitHub

上一节我们合并了工作树，但忘了让 Claude 把工作树删掉。那就回 Claude——我用 **`--resume`** 参数回到之前那段关于工作树的对话。

在这段对话里，我们能接着之前的进度，把工作树清理干净。让 Claude：「删掉 `.trees` 文件夹和底层的工作树，完成后把代码推到 GitHub。」给 Claude Code 一点时间跑必要的 git 命令——删文件夹、再把合并后的代码推上去。我们给它权限去查看底层工作树，这样不仅删掉工作树，**对应的分支也一并删掉**。

删掉这些树、移除目录、再删底层分支。做完确认一下——文件夹没了，挺好。然后把代码推到 GitHub：确认运行 `git push origin main`，代码就推上去了。

## 安装 GitHub 集成

提交并推送后，开始安装 Claude Code 自带的 **GitHub 集成**。我用 `/install-github-app` 命令。这里你可能会看到提示，需要在命令行里做额外的身份认证——看到那些设置步骤，照着做就行。

接着就能为当前仓库安装这个 GitHub app。这会打开浏览器；如果还没配置过，就有「Install」选项。

这个集成能让我们在**拉取请求和 issue** 里用 Claude Code：回应反馈、修复错误、改代码等等。这套功能的底层，是 Claude Code 自带的 **SDK（软件开发工具包）**——正是这个 SDK 让你能在终端界面之外使用 Claude Code。

回到终端，指定要安装的**工作流（workflow）**。这些工作流能让我们：在 issue 里 **@ 提及 Claude**，以及让 Claude **自动评审**我们拉取请求里的代码。两个都装。创建一个长期有效的 token，然后授权、和 Claude 完成认证。

完成后回来，会看到它在创建仓库信息、配置我需要的额外信息，再把我送回 GitHub 去**开一个包含这些改动的拉取请求**。可以看到，这个 PR 自动让 **GitHub Actions** 启用了修 bug、写测试和代码评审的能力。想改就改，或者直接用默认信息创建 PR。

这个 PR 里能看到：我们不仅为 Claude 的运行创建了一个 YAML 文件，还有一个专门做代码评审的。开箱即用就有一套挺合理的默认值：能按作者过滤、能指定运行条件。想改代码评审里的提示词，在这儿改即可；而且因为这是个被 git 跟踪的文件，你随时能改。

我把它**合并**进去，就能开始在 GitHub 里用 Claude Code 了。可以看到，一个 Claude 的 GitHub Action 已经开始跑了——这就是我们今后在 PR 里会看到的样子：它会读取并分析文件、检查代码质量、识别安全方面的考量。开箱即用，我们就多了一位新队友——Claude，来检查我们和其他成员的工作。

这有时启动得稍慢，但跑完后我们会拿到 Claude 给出的详细评估，准备好就能合并 PR。评审完了——根据我们给的提示词，可以控制想要的深度和信息量。我们能看到哪些做得好、哪些可能需要注意；觉得没问题就合并。今后的 PR 里，Claude 都会帮我们评审代码。这在「人可能漏掉某些东西、需要多一道检查」时非常有用。

## 让 Claude 在 GitHub 里修一个 issue

假设来了个 issue：团队里有人新建了一条 issue。我们可以在 GitHub 里建，也可以在 Claude Code 里建。

你可能注意到，随着我们不断往上加功能，出现了一个**新的页头**。这个新页头看着还行，但也许我们想**退回**到之前的样子。那就建一条 issue，看看 Claude 能不能帮忙。

issue 内容大致是：应用加了个新页头，请退回旧版；**保留主题切换**，但让页头恢复成以前的样子。再具体说明：去掉「Course Materials Assistant」这个页头、去掉「ask questions」附近的副标题、再去掉副标题下面那条**横线**。

建好这条 issue 后，本可以指派某人来处理，但我们干脆请 Claude 帮忙：「Claude，能帮我修一下吗？」**@ 提及 Claude** 之后，给它点时间来处理。修好后，它应该能生成一个 PR 来解决这条 issue。

给 Claude 一点时间找到那个 action。我们能看到 Claude Code 在工作，想看底层跑的 job 也能看。你看到的过程会和命令行里**非常眼熟**：分析结构、移除页头——这里我甚至能选择优先处理什么。这跟我们在终端之外看到的是一回事。我们不仅能用 Claude 处理 issue 和 PR，也能像之前那样用它评审代码。

看它的计划，能注意到它要做哪些改动、在代码库的哪里动手；顺着 PR 看，还能看到背后的思考和逻辑。这条不算难，于是它按这些步骤走：测试改动、提交、推送。它已经做了必要的提交，我们能看到底层的描述。

想的话我们可以自己创建 PR，也可以让 Claude 全包。创建 PR 时，能看到提交里到底生成了什么。来看看 Claude 做了什么：看一眼改动的文件——没改多少，可以合并。和之前一样，Claude 也会花点时间**评审它自己写的代码**。这其实挺有用：再信任 Claude，也不妨让**另一个 Claude 复查它的工作**。

看起来 Claude Code 批准了这个任务。合并它，然后回终端、把改动拉下来。我到 VS Code 里 `pull` 下改动，看看前端是不是好看些了。

成了——页头去掉了、横线也去掉了。也许我们想把那条横线请回来、或者挪到别处，但现在我们已经知道怎么做了：**不只在终端里，在 GitHub 里也能**。

## hooks：在生命周期的关键节点注入代码

再展示一个最近发布的功能——给 Claude Code 加 **钩子（hooks）**。如果你熟悉 hooks 这个概念，这会很有亲切感。思路是：在 Claude Code 的不同操作节点上（比如执行某个工具、或某个工具执行之后），我们可以**注入特定代码**，在 Claude Code 运行生命周期的任意时刻运行。

我演示给你看。回到 VS Code、再进 Claude。这些配置虽然能手动改，但我想给你看自带的编辑器：输入 `/hooks`——「管理工具事件的配置」。

你看到的画面可能有点吓人，但我们有义务提醒你：**如果你要运行任意 shell 命令，务必非常小心你在做什么。**

可以挂 hooks 的事件相当多：

- **工具执行之前**——我们甚至能**阻止**这个工具被执行；
- **工具执行之后**；
- 发出通知时；
- 用户提交提示词时；
- 某个动作停止时；
- 甚至在子代理（subagent）给出回应之前。

也就是说，我们能**用程序接入**上面任何一个事件。

我用一个 **PostToolUse**（工具使用后）的钩子举个简单例子。先加一个 **matcher（匹配器）**，在里面指定「哪些工具被用到时，这个钩子才运行」。我加个特别简单的：每当用到 **Read** 或 **Grep**，就跑一条简单的终端命令。

这条新命令是 **`say`**——它会调用电脑的音频，把你给的文字念出来。所以如果我做对了，每当读取了什么、或用 grep 在文件里找了东西，机器就会念一句「All done」。

这次还是加进**项目设置**里。前面提过 `settings.local.json` 可以指定权限——**钩子也存在这里**。进 `.claude`，在 `settings.local.json` 里能看到：除了权限，现在还有我们定义的一个钩子。`PostToolUse` 是钩子名，matcher 如果留空就匹配一切；这里写的是 Read 或 Grep 时，运行命令 `say 'All done!'`。

试试看：退出 Claude Code、再打开，让它「读取 `run.sh` 文件的内容」。这会如期用到 read 工具——「All done」。一做完，它就用语音通知我们「All done」。

这虽然是个好玩的小例子，但你可以想象用它来：**跑测试、跑代码检查器（linter）**；或者在不希望某工具被用时**阻止它**；甚至在特定情况发生时**让 Claude 评审它自己**。hooks 能做的事很多，而且还有更多功能在路上——记得去看文档，了解它的全部能力。你也随时可以让 Claude Code **帮你写 hooks、并按需修改**。
