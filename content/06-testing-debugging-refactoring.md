# 测试、调试与代码重构

现在这个代码库**缺少测试**，没法评估聊天机器人的 RAG 流程。这一节我们就来写这些测试，并用它们去**调试**一个聊天机器人处理查询时出的错；最后，再**重构**它处理工具调用的方式。开始吧。

## 出 bug 了，但别急着「截图丢给 Claude」

前面我们学了怎么快速搞懂代码库、怎么加功能。现在假设：距离上次动这个应用已经过了一阵子，我们回来想再用它。

回到应用，问一句「第 5 课讲了什么」。本来该返回信息，结果——出错了。

这时候很容易忍不住：把报错复制、丢给 Claude，或者截个图，盼着它一把解决。但我们要换种做法。

与其「拿到一个我们想要的答案」，或者把 Claude 带上一条**瞎折腾的弯路**，不如**更有章法**地来。我们知道应用出了毛病，但也知道这儿**几乎没有测试**能用程序去验证问题到底在哪。

所以我们写的提示词，不只说**错误是什么**，还**指明该在哪里写测试**。

## 锁定嫌疑文件，让 Claude 先写测试

回到代码库，这个错可能来自好几个 Python 文件：

- **`AIGenerator`**：这里处理与 Anthropic API 的交互。问题可能出在提示词，甚至出在让这块跑起来的某段逻辑里。
- **`rag_system.py`**：这是整个 RAG（检索增强生成）的总指挥。
- **`search_tools`**：这里定义底层的工具，也可能藏着问题。

我们先让 Claude 给**这几个特定文件**写测试，再让它**跑这些测试**，借此查出哪里不工作、做出恰当的修复。

这种做法强在哪？**先从测试入手**，就能给「在代码库上继续盖楼」打下一个稳固的地基，也能在出问题时搞清楚为什么会失败。

打开 Claude、贴进提示词。因为这事稍微有点难，我们还**让 Claude 多想想**——这会触发它的**扩展思考（extended thinking）** 能力，多分配一些 token 给思考过程。我们也能看到这个思考过程，一旦感觉不对，随时能把 Claude 叫停。

我们确保**计划模式开着**：在 Claude 动笔写测试之前，先让它搞懂要做什么、我们认可之后再说。它开始读必要的文件，我们能看到它的思考：不仅看到读了哪些文件，还看到它要查什么、该做什么。

看看 Claude 的计划：它觉得像是某种**配置问题**，可能是复杂的工具调用里有失败点，组件之间的错误传递也有限——所以错误有可能在某处被「吞掉」了。接着它基于这些文件提出了一套测试结构，我们看着不错：用 **pytest** 框架，把 ChromaDB 里需要的东西**打桩（mock）**，先把单元测试和集成测试跑起来。

可以看到它开始建测试文件夹、往里写测试。好的开始。我们顺手用 UV 把需要的依赖也加上。装好依赖、确认 pytest 正常工作——挺好。我们也能看到思考部分，确保做的是预期的事。随着这些测试写出来，我们就能去看它替我们写的代码：课程搜索工具的测试、需要的 fixture 和 mock……不错的开端；AI generator、RAG 系统、向量库也一样。

它似乎已经定位到一个**关键的配置问题**、可能就是这个 bug，但**写这些测试能给我们百分百的把握**——确认这确实是问题、确认这就是正确的修复。

## 跑测试，揪出真凶：`MAX_RESULTS` 是 0

测试建好后，用 UV 来跑。先确认依赖对、能正常跑测试。

根据它的发现，问题似乎出在做向量搜索时返回的 **`max_results`**（块的数量）上。我们去看看 `MAX_RESULTS` 取到了什么——果然印证了问题：不知什么原因，它居然是 **0**。把它改掉后，我们应该能看到：不仅测试如期通过，拿到的结果也完整了。我们可以验证一下，确认拿到了预期的文件。

Claude Code 收尾时会给一份详尽的总结，我可以等着看，也可以觉得没问题就把它叫停。我还是看一眼它给的：调试完成、找到了关键问题、写了几个测试，还搭了一套**能持续跑测试**的基础设施。

去看看效果。回浏览器，开个新对话，再问同样的问题。这次不该再失败，而该看到关于这节课的信息——没错，正是如此。所以我们不只修好了 bug，还给自己造了一套强大的基础设施：以后再做新改动时，能确保「东西坏了却不知道为什么」这种情况不再发生。

## 重构：让工具能多轮调用

应用跑通了。现在聊一个我想做的**重构**。`/clear`，从新功能开始。

在 `ai_generator.py` 里，我们规定**每次查询最多搜一次**。对相对简单的查询，这没问题。但当我们想做更复杂的查询——比如**对比不同课程、对比它们的大纲**——就需要**不止一次工具调用**了。所以我们需要一种机制：要么**迭代地**走完所有需要的工具，要么**递归地**解决这个问题。

如果你熟悉这段代码和生态，可以看看这里的类：它用我们的 SDK 直接和 Anthropic 模型对话，设好 `base_params`、生成响应，写法相对简单。但可以看到，在构建系统提示词、整理消息和工具的过程中，**没有迭代、没有来回**去累积所需工具、也没有「多个工具被用上的多轮对话」。

那就重构它。我这条提示词挺长，所以新建一个 markdown 文件，叫 `backend-tool-refactor.md`。我在里面让 Claude 重构后端的 `ai_generator.py`，**支持分两轮、各做一次调用**。我把**当前行为**和**期望行为**都描述清楚。这虽然不是必须的，但正如我们看到的，**给 Claude 尽可能多的信息往往很有帮助**，尤其在任务偏复杂时。

我还给 Claude 一个**示例流程**，比如「搜索一门和另一门课讨论同一主题的课程」，让它体会要做什么——注意这里就需要用到好几个不同的工具。再给一些**要求**和几条**注意事项**，确保做对。我们要求：**写测试要验证外部行为，而不是纠结内部状态的细节**。

我还让 Claude 做一件事：**先想出几套不同的方案**。先别写任何代码，而是**派出两个子代理（subagent）去头脑风暴**可能的选项。这种场景下我自己也不确定最优重构是什么，所以与其让 Claude Code 只定一个方案，不如给它机会**并行地**琢磨出多个方案。

用这条提示词，并**关掉自动接受**，好让我逐项确认每个改动。跑起来后，我们会看到它用一个叫 **task** 的工具派出**两个并行的子代理**。随着这俩 agent 被派出去，我们会拿到**两套**解决方案，由我们来决定实现哪一套。

可以看到两者并行运行、各自读文件、为这次重构琢磨出两种不同思路。结果回来了，给了推荐：一套偏**迭代**、一套更**全面**。Claude 让我们二选一：选 **B**（长期可维护性更好）或选 **A**（实现更稳妥）。往上滚能看到细节：一套支持一定程度的工具迭代，另一套实现稍复杂、用不同的辅助方法处理多轮逻辑。

第一眼看，方案 A 简单些，那就先从它入手。我选方案 A，同时**打开计划模式**，确保拿到一份完整计划、认可后再改。

实现方案 A、要一份更详细的计划来确认这正是我们想要的。我们知道得改调工具的方式，但要确保这一切都改在对的地方，再让 Claude Code 写出解决方案。

看看它要做什么：更新方法签名加上**最大轮数**、更新系统提示词，而核心重构在 `handle tool execution` 里。如果做对了，我们应该能看到：用户查询 → 调用多个工具 → 给出最终响应。这不该动其他任何东西，并能解决我们的问题。可以看到它**向后兼容**，没改内部的 RAG 系统、也没动任何 API 端点。

那就继续。随着实现推进，我们看到对现有方法的改动，更重要的是——它在**更新测试并运行测试**，验证实现是对的。不用切到浏览器、也不用找别人来测，我在 Claude Code 的终端里就全搞定了。

我们会看到它更新系统提示词、确保测试如预期，再加一个测试专门验证**顺序工具调用**没问题。跑测试，确认全过。

## 在浏览器里验收

到浏览器验证。先问某门课某节课的细节。可以看到，我们不仅拿到了信息，还如期拿到了**标题**——拿到这节课的信息，以及讨论到的部分章节和主题。

现在来点更复杂的。能拿到标题之所以特别，是因为**单次工具调用是拿不到的**：第一次工具调用只给课程大纲，第二次才给某节课的细节（这里就是标题）。

我们问：「有没有别的课程，和 MCP 这门课第 5 课讲同一个主题？」要回答这个，就得**多次工具调用**——先拿 MCP 这门课的信息和大纲，再拿其他课程及其大纲，看看有没有重叠。可惜，看起来没有别的课程讲「构建 MCP 客户端」，这结果确实准确。

这一节，我们看到了怎么用 Claude Code **不仅修 bug，还在整个过程中写测试**。我们给自己打下了一个能继续写代码的坚实地基，还做了一次漂亮的重构，让更复杂的查询也能被妥当回答。

下一节，我们会**用工作树（Git worktree）同时跑多个 Claude Code 会话**来提升效率，并确保它们之间不会重叠或互相覆盖。到时见。
