# 同时并行开发多个功能

你可以开**多个** Claude Code 会话，并行地做很多功能。为了管好这些会话、避免它们改同一个文件造成覆盖，你可以用**工作树（Git worktree）**。这一节，我们就用工作树**并行**给聊天机器人加三个功能。

## 先做一个自定义斜杠命令

回到 Claude。前面看到 Claude Code 内置了不少斜杠命令（slash command），但你也能**自己造**。

做自定义命令，要在 `.claude` 文件夹里新建一个 `commands` 文件夹，里面放一个 markdown 文件、文件名就是命令名。我要做的命令叫 **implement feature**，于是建一个 `implement-feature.md`。

文件里想写什么都行。但有个很特别的地方要给你看：如果你想给自定义命令**传参数**，可以用 **`$ARGUMENTS`** 这个变量来引用。我这里写的意思是：这个命令一被调用，就表示「你要实现一个新功能」，具体是什么功能由用户传进来；同时我要确保 Claude Code 清楚——**只针对前端功能**做，并把改动写进一个叫 `frontend-changes.md` 的文件。

可以想象，自定义命令有很多用法：你想用某种方式跑测试、跑文件等等。注意，这里写的内容**不会自动进入你的上下文**（这点和 `CLAUDE.md` 不同）。所以——

- 想让某些东西**应用到你创建的每一个 Claude Code 实例**，写进 `CLAUDE.md`；
- 只是一些**不同对话里时用时不用**的特定命令，放这里就很合适。

我之后讲工作树时会用到这个自定义命令。先退出 Claude Code 再进来，验证一下能看到它——能看到 `implement feature`，描述就取自这个 markdown 文件的开头部分。

加了这个自定义命令后，我们 add、commit 它。我本可以在命令行手动做，但我让 Claude 来：「把所做改动 add 并 commit。」这样 Claude Code 能写出一条带描述性信息的漂亮提交信息。可以看到它把 `.claude` 文件夹加上、用必要的命令提交了——已进仓库。因为之前已经授过权，这次不用再确认。

> 想知道权限存在哪？在 `.claude` 文件夹里有个 `settings.local.json`。里面可以指定**你允许了哪些命令**，省得每次都确认。可以看到，之前用 Playwright 时给的权限也在这儿。想加自己的，在这个文件里改就行，或者用顺手的 `/permissions` 命令。

## 为什么需要工作树

自定义命令配好了，来聊聊怎么**并行**用 Claude Code。

我们不只是开一堆终端窗口、都直接在这个代码库上干。因为如果我有**两个 Claude Code 实例改同一个文件**，在当前这种环境下就会**互相覆盖、制造 bug、一团乱**。所以我们要用 Git，确保多个实例并行时不会覆盖现有文件。

好在 Git 有个绝佳的功能叫 **worktree（工作树）**。工作树能让我本质上**创建代码库的多份副本、各自隔离地干活，最后再合并到一起**。而且，合并和管理这些工作树，我也能让 Claude 来帮忙。

## 建三个工作树

上手工作树：我先建一个文件夹叫 `.trees`，往里加几个工作树。用 `git worktree add` 命令，指定文件夹和我想加的工作树名字。建三个：

- `ui_feature`
- `testing_feature`
- `quality_feature`

确认一下：我现在在 main 分支上，已经建好了三个独立的工作树。

为了在每个环境里都配置好，我打开 `.trees` 文件夹，给每个工作树**各开一个终端**：`ui_feature` 拖过来、`testing_feature` 放旁边、`quality_feature` 放上面。腾点地方、把界面缩小，现在就有了三个专属终端窗口（把文件浏览器也藏起来）。然后，给每个环境各开一个 Claude。

## 三路并行开工

现在我们能**并行**跑 Claude Code，即便改了相同文件也不会互相覆盖——之后合并工作树时再处理。

在第一个工作树里，我用 `implement-feature` 命令，传入功能：**加一个在深色/浅色主题间切换的开关按钮**。那就先做出这个开关、摆好位置、确保能用；先做这部分，再补上浅色主题的变体。

它在跑，我转到第二个工作树。这里我想想**测试框架**要干啥，传入提示词：**增强现有测试框架、为 FastAPI 端点补充更多测试**。趁这个在跑，再去第三个：给开发流程加上一些**必要的代码质量工具**。

随着推进，能看到各处都在请求改动。于是我在这几个环境间来回切、确认想要的改动。测试在写、用于分析代码结构和格式化的额外开发依赖也在加。这里会看到它在改 `pyproject.toml`，也会看到一个编辑这个文件的请求。

> 注意：`pyproject.toml` 这个文件在**两个不同的工作树**里都被改了，所以待会儿合并时可能会有冲突。

我们能并行干活，并确保这些改动不会被代码库别的部分覆盖；万一对相似文件做了改动，我们也能把合并冲突修好——用 Claude 来修。前端改动在写、测试在加、格式化工具和质量检查的开发脚本也在加。

继续推进、确保质量脚本就位、前端功能也在添加。现在像之前一样**加上浅色主题**——用 `implement feature` 自定义命令，确保把它写进我们的变更日志，再加上浅色主题。完成后，再排队几个关于 JavaScript 功能和实现细节的提示词。

趁它跑，我去看看别的脚本，确认要运行它们；有情况的话 Claude Code 能按需修。看起来有些脚本 Claude 不认识，那就装依赖、或确保按预期运行。可以看到：先从代码质量检查开始，写好了 API 端点测试，又在加更多前端功能。

## 合并：让 Claude 处理冲突

全部做完后到浏览器看。在那之前，先把这些零散改动**各自 add、commit**，配上**描述性的提交信息**——因为我们要合并这些提交，得让每个工作树里做了什么一目了然。三个工作树都这么做：测试功能提交、UI 增强提交、质量功能提交。

> 小贴士：如果你发现自己老在写「add 并 commit、配描述性信息」这种提示词，这又是一个适合做**自定义命令**的场景——可以把你想要的风格、或公司的 Git 最佳实践固定下来。

三个都提交完，我就能回到 main 分支做合并了。关掉这些终端环境、回到主环境。

我让 Claude：**用 `git merge` 命令，把 `.trees` 文件夹里所有工作树合并进来，有冲突就修掉。** 让 Claude Code 合并这些树、确保如期工作。可以看到有三个工作树可用，于是逐个合并。确认这是我们要用的命令——

- `testing_feature`：没有冲突。
- `ui_feature`：合并进来。（这些命令我们也能自己写，但 Claude Code 从提示词就知道该怎么做。）
- `quality_feature`：这里**有冲突**——正是之前那个文件。

那就让 Claude Code **分析这些冲突、完成合并**。当你遇到不想每次手动处理的小合并冲突时，这特别有价值。这时候**有测试**也很值钱：合并完能跑测试，确认代码库如期工作。它继续完成合并，并把解决了冲突的改动一并提交。

完事后我可以让它**删掉**这些工作树，也可以留着备用。我快速测一下，确认文件都在、合并配置也符合预期。再回浏览器，看看前端改动是否如期实现。

看来 Claude Code 收工了：装了必要依赖、改了 `pyproject.toml`、加了测试、实现了深浅主题、接入了 **black** 代码格式化器（确保代码按指定格式），并把配置加进了那个「另一个工作树也动过」的同一个文件里。冲突也修好了。

回浏览器确认：现在有了这个漂亮的主题，来回一切——浅色、深色都在。也许还有些地方想再微调，但我已经能**横跨整个技术栈**做改动，连 linting 和 DevOps 那块也搞定了，**全程没有覆盖、没有恼人的麻烦**——靠的就是 Git worktree 的威力。

下一节，我们会看看怎么在**终端之外**用 Claude Code——通过和 GitHub 的集成来评审拉取请求（pull request）、做改动，在终端生态之外也能帮上忙。
